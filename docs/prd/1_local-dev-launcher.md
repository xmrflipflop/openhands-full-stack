# PRD: Local development launcher

**Status:** Active

## Summary

Run the Agent Canvas frontend and the OpenHands Agent Server backend together, built strictly from the source in this repository, so the two subtrees can be developed and validated against each other. The upstream `agent-canvas` CLI runs a similar stack but installs released artifacts (the agent-server from PyPI via `uvx`, the frontend from the published npm package); this workspace runs the same workflow pointed at local sources instead. The frontend is served differently per role: dev runs the Vite dev server (`react-router dev`); prod runs upstream's `static-server.mjs` against a prebuilt SPA, because the Vite dev server cannot run under `NODE_ENV=production` (the prod role's `NODE_ENV`).

Process management is **PM2**, driven by a single committed `ecosystem.config.js` that derives everything from where it is running. There is no custom launcher script: the ecosystem reads the checkout's role and identity from the filesystem and computes app names, ports, namespace, and `NODE_ENV` from them. The two operating modes are intentionally distinct:

- **Dev (foreground).** `just dev` runs `pm2-runtime` in the foreground against a throwaway `PM2_HOME`, so the dev run never touches the global `~/.pm2` daemon. Logs stream to the terminal; Ctrl-C stops the whole stack; there is no state to manage, save, or resurrect. This is the day-to-day developer loop.
- **Prod (detached).** A checkout under `/opt` is started with plain `pm2 start ecosystem.config.js` against the global daemon, then managed with PM2's own verbs (`pm2 ls`, `pm2 logs`), snapshotted with `pm2 save`, and restored across machine restarts with `pm2 resurrect`. The id-from-path/id-from-file derivation is read fresh on every evaluation, so resurrected instances come back with the correct ports.

## Scope

Workspace-owned only; no upstream files are modified.

| Path | Role |
| --- | --- |
| `ecosystem.config.js` | The single committed PM2 process ecosystem (workspace-owned). Derives role, identity, app names, ports, namespace, and `NODE_ENV` from the checkout location and a per-checkout id; defines the uv-venv interpreter and supervision limits; selects the upstream serving seam per role (dev: `react-router dev`; prod: `static-server.mjs` + built SPA). No secrets or env-specific values are hard-coded in app code. |
| `scripts/dev-local-ingress.mjs` | The single-origin ingress app (workspace-owned), the third PM2 app. A thin wrapper over the upstream ingress that adds only a bind address; its existence is justified in `docs/prd/4_ingress-host-wrapper.md`. |
| `justfile` | The `setup` recipe: bootstraps dependencies for every role (alloc `.dev-id`, `uv sync`, `npm install`); `just setup --prod` additionally builds the Agent Canvas production bundle (the artifact the prod static server serves — FR13b). |
| `.gitignore` | Ignores the per-checkout identity file, the uv venv, node_modules, PM2 runtime state, and the prod frontend build output. |
| `packages/agent-canvas` | Consumed: the frontend dev server and its dev-proxy / configuration surface (dev); the `static-server.mjs` static + reverse-proxy script and the `npm run build` target (prod); the ingress script and proxy internals consumed by the wrapper. The package's `build/` directory (the prod bundle output) is produced and consumed by the prod path; it is gitignored and regenerated by `just setup --prod`, not committed. |
| `packages/software-agent-sdk` | Consumed: the agent-server entry point and its uv workspace; the `uv sync`-managed `.venv` is the PM2 backend interpreter. |

### Retired by this revision

This revision replaces an earlier, over-engineered build with direct PM2. The following workspace-owned files (no longer in the tree) are **removed** by the migration to this PRD:

| Role it played | Notes |
| --- | --- |
| The pre-PM2 foreground shell supervisor | Process-group-based crash-linked supervision. Replaced by PM2. |
| The bespoke PM2 launcher | A flag surface, hash-derived names, per-deployment `PM2_HOME` isolation, a "last started" name file, and orphan-reaping logic. Replaced by the self-deriving ecosystem. |
| The backend entry shim | A PM2 file-path entry point for the agent-server. Retired in favor of pointing PM2's `script` at the venv `agent-server` console script directly. |

## Functional requirements

- **FR1** — A single committed `ecosystem.config.js` at the repo root defines every app. It derives role, identity, app names, ports, namespace, and `NODE_ENV` from the checkout location and a per-checkout id at evaluation time, so starting (in either foreground-dev or detached-prod mode) requires no per-invocation flags to produce a correct, clash-free deployment.
- **FR2** — Role comes from the checkout path. A checkout located under `/opt` is **prod** (exactly one, fixed base ports). Any other checkout location is **dev**. The role selects `NODE_ENV` and the port block.
- **FR3** — Each non-prod checkout carries a `.dev-id` file containing a positive integer, unique per checkout (e.g. `1`, `2`, … across worktrees). The ecosystem reads it fresh on every evaluation; a missing or invalid `.dev-id` for a non-prod checkout is a hard error that aborts the start, so a clash can never happen silently. `.dev-id` is gitignored and never committed. Allocation is automated in `just setup` (idempotent, with main-clone and git-worktree rules) by `scripts/alloc-dev-id.sh`, owned by `docs/prd/5_devid-worktree-allocation.md`; the ecosystem remains the consumer and validator and does not allocate on its own.
- **FR4** — The id (treated as `0` for prod) is the single source of truth: the app-name tag, the PM2 namespace, and the frontend/backend port block all derive from it. Because names are derived from the id, name uniqueness implies port uniqueness; there is no independent port to misconfigure.
- **FR5** — PM2 app names are `<service>-<tag>` where `tag` is `prod` or `dev<N>` (e.g. `backend-prod`, `backend-dev1`, `frontend-dev2`). The PM2 `namespace` is the tag, so group operations (`pm2 restart prod`, `pm2 stop dev2`) and single-app operations (`pm2 logs backend-dev1`) both work naturally.
- **FR6** — Concurrent deployments never clash on ports or app names: the id-derived port block and tag keep dev checkouts (distinct `.dev-id`) and the single prod checkout disjoint. Because dev runs in the foreground against a throwaway `PM2_HOME`, the supported concurrent case is one foreground dev stack per terminal plus any detached prod; two simultaneous foreground dev stacks sharing the same throwaway home would collide on the daemon socket, so a second concurrent dev checkout must use a distinct `PM2_HOME`.
- **FR7** — The backend runs from local `packages/software-agent-sdk` sources and is launched with the repository's uv-managed virtual environment specified explicitly as PM2's `interpreter` (not system Python, not `uvx`, not a PyPI release). `uv sync` materialises that venv with workspace members in editable mode before start, so every `openhands-*` package resolves to local sources. No `openhands-*` release may be fetched from a registry. PM2's `script` points at the venv's installed `agent-server` console script (under `packages/software-agent-sdk/.venv/bin`); the venv python is the `interpreter`, so the composed command is `<venv>/bin/python <venv>/bin/agent-server --host .. --port ..` and the installed package imports cleanly.
- **FR8** — The frontend is the local `packages/agent-canvas` application. The published `@openhands/agent-canvas` package must never be installed or executed. The two roles serve the frontend through different upstream seams (no upstream file is patched; the ecosystem only configures/consumes them), because the two roles run under a different `NODE_ENV` (FR10) and the Vite dev server cannot run under `NODE_ENV=production` — Vite's SSR JSX transform then imports `react`'s production `jsx-runtime` (which has no `jsxDEV` export), and the dev server crashes with `jsxDEV is not a function` (plus a downstream `Cannot access 'abort' before initialization` TDZ crash from the abort timer). The two serving paths:
  - **dev** runs `react-router dev` (the Vite dev server, via the `dev:frontend` package script). Its built-in dev proxy targets the backend at the backend's derived port: the launcher exports the backend's `host:port` as `VITE_BACKEND_HOST`, consumed only server-side by the Vite config's dev-proxy entries; the app's browser-side agent-server base-URL lookup never reads it.
  - **prod** runs the upstream `packages/agent-canvas/scripts/static-server.mjs` against the production bundle in the package's `build` directory (regenerated out-of-band by `just setup --prod`; see FR13b). The static server serves the prebuilt SPA with history-mode fallback and its own reverse proxy forwards the same `/api`, `/sockets`, … prefix set used by the ingress (a single workspace-owned `backendRoutes` list), so the prod frontend port behaves like Vite's dev server even though no dev server runs. The session API key is injected into the served `index.html` at runtime via `--session-api-key` (not baked into the build), preserving FR8b for the served bundle. The ecosystem fails fast with a clear message if the build's entry file is absent at evaluation time rather than serving nothing.
- **FR8a** — No server-local backend address (host:port) is baked into anything the browser executes. The frontend app's agent-server base URL must resolve, at runtime in the browser, to the same origin that served the page. The launcher therefore exports `VITE_SESSION_API_KEY` (so the "configure a backend" onboarding prompt is never raised) and `VITE_BACKEND_HOST` (consumed only server-side by the dev-server path), and deliberately **omits** `VITE_BACKEND_BASE_URL` so the app's same-origin fallback — the page's own origin when no base URL is configured — is what the browser uses. This applies identically to dev and prod: the launcher never branches on role for the browser-facing env it exports. The same-origin promise is honoured server-side by two different paths — the ingress's prefix routes (the `/api`, `/sockets`, … set) when the browser arrives through the ingress port, and **either** the Vite dev proxy's own entries (dev, FR8 dev) **or** the static server's own reverse proxy (prod, FR8 prod) when it arrives through the frontend port; both forward to the backend's loopback port on the server, where that address is valid. (A previous form baked `VITE_BACKEND_BASE_URL=http://127.0.0.1:18000`; remote browsers then dialed their own loopback. Withholding it is the fix.)
- **FR8b** — The launcher guarantees a non-empty session API key (`OH_SESSION_API_KEYS_0` for the backend, `VITE_SESSION_API_KEY` for the frontend) — this is what makes the same-origin+key arrangement in FR8a actually suppress the "configure a backend" prompt: the frontend's default-local-backend constructor returns null on an empty key, so an empty key would re-surface that prompt regardless of the same-origin fallback. Resolution order, mirroring the upstream `agent-canvas` CLI and the predecessor `openhands-full-stack` workspace's shell launcher: (1) an explicit `LOCAL_BACKEND_API_KEY` env var takes precedence; otherwise (2) read the key persisted at `~/.openhands/agent-canvas/dev-local-api-key` (overridable via `OH_SESSION_API_KEY_PATH`); if that file is missing or empty, (3) generate a fresh 256-bit (64-hex-char) key with the operating system's CSPRNG and persist it to that path. The persisted key is stable across `just dev` restarts and shared with the published CLI and the predecessor shell launcher, so the frontend's cached backend-registry entry (keyed on host+key) keeps working. The key file is written mode `0600` (credential) under a home-directory path that is never committed. This applies identically to dev and prod: the key derivation sits in the shared block that runs for every role.
- **FR9** — The whole stack is additionally served behind a single origin (one host:port, the ingress app) that routes API and websocket paths to the backend and everything else to the frontend, so the browser makes same-origin API/websocket calls. The ingress is the third PM2 app, run by `scripts/dev-local-ingress.mjs` (justified in `docs/prd/4_ingress-host-wrapper.md`). Its bind address is controllable (loopback by default; exposed on demand).
- **FR10** — `NODE_ENV` is derived from role: prod → `production`, dev → `development`. It is the only env-mode variable any application code reads (the frontend uses it for i18n debug logging and an `isDevMode` flag; the backend ignores it). There are no named runtime-environment blocks (`env_staging` / `env_production`) and no `--env <name>` selection — the earlier named-environment machinery was removed because `DEV_ENV_NAME` was set but never consumed and the blocks differed only in `NODE_ENV`, which role already determines. This derivation is only sound because each role serves the frontend through a NODE_ENV-appropriate upstream seam (FR8): dev runs the Vite dev server under `NODE_ENV=development` (its SSR pipeline needs `react`'s dev JSX runtime); prod serves a prebuilt bundle under `NODE_ENV=production` (the dev server's `jsxs`/`jsxDEV` path is never exercised). Running the dev server under `NODE_ENV=production` (an earlier form) made Vite import `react`'s production JSX runtime (no `jsxDEV`) and crashed the server with `jsxDEV is not a function` — the very defect the dev/prod serving split exists to avoid.
- **FR11** — PM2 supervises frontend, backend, and ingress with bounded auto-restart: `autorestart`, a `max_restarts` limit, `min_uptime`, `restart_delay`, and a `max_memory_restart` threshold. A process that repeatedly fails within its minimum-uptime window is held in `errored` state rather than spinning.
- **FR12** — The stack runs unprivileged: no port below 1024 is bound, and all writes stay inside the checkout. Root is not required for normal operation. Privilege drop via PM2 `uid`/`gid` is documented but disabled by default and only honoured when PM2 is started as root.
- **FR13** — Two operating modes use the same `ecosystem.config.js` differently: (a) **dev** is foreground via `pm2-runtime` with a throwaway `PM2_HOME` (set by `just dev`), so the dev run never touches the global `~/.pm2` daemon; Ctrl-C stops the whole stack and there is no state to manage. (b) **prod** is detached via plain `pm2 start ecosystem.config.js` against the global daemon, then managed with PM2's own verbs (`pm2 ls`, `pm2 logs <app>`), snapshotted with `pm2 save`, and restored across machine restarts with `pm2 resurrect`.
- **FR13b** — Prod requires a built frontend bundle that the prod static-server app serves (FR8 prod). The build is **out-of-band** — not part of the PM2 lifecycle — and regenerated by `just setup --prod` (or directly `cd packages/agent-canvas && npm run build`) as a separate, idempotent step. `just setup` (no flag) intentionally does **not** build it, so dev checkouts skip the cost; the prod operator runs `just setup --prod` before `pm2 start ecosystem.config.js`. The ecosystem's prod role fails fast with a clear message if the build's `index.html` entry is absent at evaluation time (so a missing build surfaces immediately rather than serving nothing). The build output is gitignored and never committed.
- **FR14** — `just dev` is a thin wrapper that runs `pm2-runtime start ecosystem.config.js` against a throwaway `PM2_HOME`. It is not a supervisor, adds no process-management logic of its own, and exposes no dev-specific stop/restart/status/logs/save verbs — foreground `pm2-runtime` and PM2's own verbs cover all of it. The throwaway home keeps dev state out of the global daemon where prod lives.

## Non-functional requirements

- **NFR1** — Portable, POSIX-only scripting where any scripting is needed (the Coder host and contributor laptops may run macOS bash 3.2).
- **NFR2** — The id-from-path and id-from-file derivation is read fresh on every PM2 evaluation, so a detached-prod `pm2 resurrect` brings the prod instance back with the correct ports after a machine restart. Dev runs are foreground and throwaway: nothing is saved or resurrected for dev, so there is no dev state to drift.
- **NFR3** — No credentials, tokens, or `.dev-id` values are committed. The `.gitignore` covers `.dev-id`, venvs, node_modules, and PM2 runtime state.
- **NFR4** — Concurrent checkouts never collide: the id is the single source of truth for names and ports, and a missing/invalid `.dev-id` fails fast.

## Decision points

- **Self-deriving ecosystem vs. a custom launcher script.** Chose the self-deriving ecosystem. The earlier bespoke launcher accumulated a flag surface, hash-derived names, per-deployment `PM2_HOME` isolation, a "last started" name file, and orphan-reaping logic — far more machinery than the problem needs. Deriving role and identity inside `ecosystem.config.js` from path and `.dev-id` keeps one source of truth and lets PM2's own verbs do all the work.
- **Role from path vs. an explicit `--role` flag.** Path is automatic and unambiguous for the `/opt` = prod convention; it cannot be forgotten on a start.
- **`.dev-id` file vs. a derived/hash id.** A small explicit file is the clearest single source of truth, is unique per checkout, and survives `pm2 save` / `pm2 resurrect` (the id is read fresh each evaluation and baked into the snapshot). A hash of the path would also be unique but is opaque and harder to reason about for `pm2 logs backend-dev1`.
- **Single shared PM2 registry + namespaces vs. per-deployment `PM2_HOME` isolation.** Chose shared + namespaces. The prior per-deployment `PM2_HOME` was over-isolation: it defeated PM2's group operations, required a custom wrapper to find the right registry, and made orphan reaping necessary. A single registry with `namespace` per instance gives `pm2 restart prod` / `pm2 stop dev2` for free and one `pm2 resurrect` to restore everything.
- **Single-origin ingress vs. frontend dev proxy alone.** Kept the single-origin ingress as the third PM2 app (Option B), so the whole stack is served behind one host:port and the browser makes same-origin API/websocket calls. Because the upstream ingress cannot bind a host, it runs through the thin workspace-owned wrapper `scripts/dev-local-ingress.mjs` (justified in `docs/prd/4_ingress-host-wrapper.md`); the frontend's built-in dev proxy is not relied upon for the single-origin contract.
- **Backend launch: venv console script vs. `uv run` / a workspace shim.** PM2 resolves its `script` field as a file path and cannot run `python -m openhands.agent_server` directly; pointing at the package `__main__.py` shadows the installed package on `sys.path[0]`. The SDK's installed `agent-server` console script (under the venv's `bin`) is a file path whose own body is a clean `from openhands.agent_server.__main__ import main; sys.exit(main())`, so pointing PM2's `script` at it with the venv python as `interpreter` runs the server with no shadowing and no workspace-owned shim. A workspace shim was considered and rejected as redundant: it would duplicate the console script's body. Using `uv run` was rejected because it adds a wrapper process and keeps PM2's process tree non-flat.
- **Prod under `/opt` vs. an environment variable.** The path convention is chosen because the prod checkout's location is itself the deployment signal in the Coder setup. Note the Coder caveat: `/opt` is typically not on the persistent home volume, so the prod clone (and its `chown` to the unprivileged user) belongs in the image or startup script, and `pm2 save` must be re-run whenever the set of instances changes.
- **Foreground `pm2-runtime` (dev) vs. detached `pm2 start` (prod).** Dev runs in the foreground against a throwaway `PM2_HOME` so it never touches the global `~/.pm2` daemon where prod lives: logs stream inline, Ctrl-C stops everything, and there is no state to manage, save, or resurrect — which removes the need for dev-specific stop/restart/status/logs/save wrapper recipes entirely. Prod keeps the detached `pm2 start` + `pm2 save` + `pm2 resurrect` lifecycle because it must survive the operator disconnecting. Rejected for dev: a detached daemon with wrapper verbs — more machinery than the foreground loop needs.
- **Derived `NODE_ENV` vs. named runtime environments (`--env`).** The ecosystem originally provided `env` / `env_staging` / `env_production` blocks selectable with `--env <name>`. Removed in favor of deriving `NODE_ENV` from role (prod → `production`, dev → `development`). `DEV_ENV_NAME` was set but consumed by nothing; the blocks differed only in `NODE_ENV`, which role already determines. The only readers of `NODE_ENV` are the frontend's i18n debug logging and an `isDevMode` flag (the backend ignores it). This derivation is only sound because each role serves the frontend through a NODE_ENV-appropriate seam (see the next decision); the prior belief that `--prod`/`--dev` differed "only in NODE_ENV, which role already determines" was incomplete because the dev server itself reads NODE_ENV.
- **Dev-server (dev) vs. served SPA (prod) for the frontend — the decision forced by `jsxDEV`.** Originally BOTH roles ran `react-router dev`, with prod under `NODE_ENV=production`. That crashed prod: Vite's SSR JSX transform imports `react`'s production `jsx-runtime` (exports `jsx`/`jsxs`, **no** `jsxDEV`) under `NODE_ENV=production`, but the compiled entry-server file calls `jsxDEV`, so the dev server threw `jsxDEV is not a function` (and a downstream `Cannot access 'abort' before initialization` TDZ crash from the abort timer). Two fix shapes were considered: (a) override `NODE_ENV=development` for the prod frontend dev server and keep running a dev server in prod (cheap, but ships live dev-server overhead + HMR plumbing to prod and leaves "prod" mislabeled); (b) build the prod bundle and serve it through the seat upstream already provides — `packages/agent-canvas/scripts/static-server.mjs` (static files + history fallback + reverse proxy) — with `NODE_ENV=production` left correct (chosen). The served-SPA path needs the same single-origin and session-key contracts as the dev path: the static server's own reverse proxy reuses the workspace `backendRoutes` list the ingress uses (FR8a), and the session key is injected into the served `index.html` at runtime via `--session-api-key` rather than baked into the build (FR8b). The build is kept out of the PM2 lifecycle and regenerated by `just setup --prod` (FR13b). No upstream file is patched: the ecosystem only configures the two upstream seams (`react-router dev` / `static-server.mjs`). Rejected: patching Vite/the entry-server to run the dev server under `NODE_ENV=production` — that would be a workspace patch inside `/packages/`, merge-debt on every subtree sync, and working around a correct Vite behavior.
- **Withhold `VITE_BACKEND_BASE_URL` vs. bake a server-local address.** The launcher exports `VITE_SESSION_API_KEY` and `VITE_BACKEND_HOST` (server-side only) and omits `VITE_BACKEND_BASE_URL`, so the app's browser-side base-URL lookup falls back to the page's own origin (FR8a). Baking a server-local base URL (the earlier form) was rejected because it is shipped verbatim into the browser bundle: a remote browser would then dial its own loopback for the backend, and an operator exposing the stack beyond loopback would have to hand-edit the bundle per host. Withholding it makes the backend address *implicit from where the page was served*, requires no per-host configuration, and works for both dev and prod without branching on role. The cost is a hard dependency on the app keeping that same-origin fallback (see Assumptions); if upstream ever makes a configured base URL mandatory, a replacement same-origin mechanism must be found before the stack can be sync'd.
- **Auto-generate-and-persist the session key vs. require the operator to supply one.** Chose to auto-generate. An earlier form only *read* the persisted key and, when it was absent or empty, fell through to an empty `VITE_SESSION_API_KEY` — which silently broke FR8a: the frontend's default-local-backend constructor returns null on an empty key, so the "configure a backend" prompt fired for every fresh browser even though the same-origin fallback was in place. Auto-generating and persisting a 256-bit key (precedence: `LOCAL_BACKEND_API_KEY` env → `~/.openhands/agent-canvas/dev-local-api-key` → generated) is exactly what the upstream `agent-canvas` CLI and the predecessor `openhands-full-stack` workspace's shell launcher do, so the key is stable across `just dev` restarts, shared with the published CLI, and the frontend's cached backend-registry entry keeps working. Rejected alternatives: requiring the operator to set `LOCAL_BACKEND_API_KEY` (raises the barrier to a first run and offers no benefit, since the key is meaningless outside this stack); or persisting per-checkout under `.pm2-runtime/` (rejected because the home-dir path matches upstream and the predecessor shell launcher, avoids piling a second key file alongside the existing one, and the key's identity does not need to vary per checkout since each checkout runs its own backend anyway).

## Assumptions (re-check these first when upstream changes)

- `pm2` (any current v7+) is installed on contributor machines, in CI, and in the Coder image.
- The Coder host convention holds: the prod checkout lives under `/opt`; dev checkouts (including git worktrees) live elsewhere, typically under the home tree.
- The SDK remains a single uv workspace whose members include the agent-server; it exposes a runnable agent-server entry point accepting host and port options; and `uv sync` materialises a `.venv` whose `python` can import and run the agent-server entry function.
- The frontend keeps a `dev:frontend` package script that starts only the dev server (without spawning backends), honours environment configuration for its port and backend host, and proxies API/websocket paths to the configured backend. (Consumed only by the **dev** serving path — FR8 dev. The prod serving path does not use this script.)
- The frontend ships a `build` / `build:app` package script that produces a production SPA bundle, and that bundle's output — after any post-build directory flattening upstream performs (e.g. the `unpackClientDirectory` move in the package's react-router config) — is a directory whose entry is `index.html` (the served entry) with the hashed assets under it. The prod static-server serves that directory. **Re-check on upstream sync**: if the build output layout changes (entry location, asset paths, or the directory-flattening moving the entry out of the build directory's `index.html`), the prod stat path and/or the `--dir` path passed to the static server must be updated; the ecosystem's prod build-guard keys on that entry file.
- The frontend ships a `packages/agent-canvas/scripts/static-server.mjs` (the `--start`-equivalent static + reverse-proxy script) that accepts `--dir`, `--port`, `--host`, `--route <prefix=url>` (repeatable, websocket-aware), `--session-api-key` (injects `window.__AGENT_CANVAS_SESSION_API_KEY__` into the served `index.html` at runtime), and history-mode SPA fallback. The prod frontend app pins to that script's CLI surface. **Re-check on upstream sync**: if the static server's flag names, the key-injection seam (`__AGENT_CANVAS_SESSION_API_KEY__` → `getBakedSessionApiKey()`), or the runtime-injection mechanism change, update the ecosystem's prod args and re-assert FR8b for the served bundle before relying on it.
- The frontend's dev-proxy host configuration (`VITE_BACKEND_HOST`) is consumed only server-side by the Vite config, never by the browser-side app; it is distinct from the browser-side base-URL configuration. (Dev only.)
- **Same-origin fallback (the load-bearing assumption for FR8a).** The frontend app's agent-server base-URL lookup returns a configured base URL when one is present, and otherwise falls back to the page's own origin (`window.location.origin`). The launcher relies on this fallback to *never* bake a server-local address into the browser bundle. **Re-check this first on every upstream sync**: if upstream ever makes a configured base URL mandatory (no fallback, or the fallback removed), the launcher's withholding of that URL would re-surface the "configure a backend" prompt for remote browsers, and a replacement same-origin mechanism must be found before the stack can be sync'd.
- **Session-key-onboarding interplay (the second load-bearing assumption for FR8a / the one that drove FR8b).** The frontend's default-local-backend constructor (`makeDefaultLocalBackend()`) returns null unless **both** a non-empty base URL *and* a non-empty session API key are available — an empty/whitespace key is treated as missing, so the backend registry is left empty and the "configure a backend" onboarding prompt fires regardless of the same-origin fallback. The launcher MUST therefore guarantee a non-empty key for **both** serving paths: in dev by exporting a non-empty `VITE_SESSION_API_KEY` (consumed at build/dev time), and in prod by passing the same key to `static-server.mjs --session-api-key`, which the static server injects into the served `index.html` as `window.__AGENT_CANVAS_SESSION_API_KEY__` (read at boot by `getBakedSessionApiKey()`). **Re-check on upstream sync**: if either the env-var consumer OR the `--session-api-key` → `getBakedSessionApiKey()` injection seam is removed, the corresponding serving path would silently regress to an empty key and re-surface the onboarding prompt; a replacement seam must be wired on the affected path before the stack can be sync'd.
- The frontend's backend-host configuration (dev) accepts a `host:port` value that the dev proxy forwards to, the static server's `--route` values (prod) accept `<prefix>=http://host:port`, and the frontend's backend-base-URL configuration (when set at all) accepts a full `http://host:port` value the browser uses directly.
- The workspace's `backendRoutes` list (`/api`, `/sockets`, `/server_info`, `/alive`, `/health`, `/ready`, `/docs`, `/redoc`, `/openapi.json`) tracks the Vite dev-proxy prefix list (`packages/agent-canvas/vite.config.ts`). It is shared by the ingress (both roles) and the prod static server's `--route` flags. **Re-check on upstream sync**: if the Vite dev-proxy prefix set changes (paths added/removed/renamed), update `backendRoutes` in the ecosystem in the same change so all three proxying paths keep routing identically.

## Upstream divergence

No upstream code is modified; the divergence is behavioral. Upstream's launcher installs released artifacts by design; this one forbids that and runs local sources, so it is not upstreamable as-is. If upstream ever ships a supported "run everything from a local checkout" mode covering both projects, this functionality can be retired in its favor.

The PM2 ecosystem is workspace-owned; it is not an upstream contribution because upstream does not supervise its launcher with PM2. The backend launch uses the SDK's own installed `agent-server` console script (no workspace-owned backend entry file). The prod frontend app launches the upstream `static-server.mjs` and builds the upstream `build`/`build:app` target — both only configured/consumed, not patched. The role-based choice of which upstream seam to serve the frontend through (dev: `react-router dev`; prod: `static-server.mjs`) is workspace behavior layered on top of upstream's existing two serving modes; upstream never needs to adopt it.

## Conflict resolution notes

Preserve the requirements, not the implementation. If an upstream update breaks the stack, re-locate the SDK's current way of running the agent-server from workspace sources (`uv sync` + the venv python) and the frontend's current dev-server script and configuration surface (dev), the current `build`/`build:app` target and its output layout (prod build), and the current `static-server.mjs` CLI surface and runtime key-injection seam (prod serve), then rewire the ecosystem to them. Any functional requirement may be reimplemented with different mechanics; none may be dropped silently. The stable invariants are the id-from-path/id-from-file contract (FR2–FR4), the local-sources-only contract (FR7–FR8), the uv-venv-as-interpreter contract (FR7), the role-appropriate-serving-seam contract (FR8 dev/prod — the dev server MUST NOT run under `NODE_ENV=production`), the no-baked-server-local-address / same-origin contract (FR8a — honored on both serving paths via the ingress OR the static server's own proxy), the guaranteed-non-empty-session-key contract on both serving paths (FR8b — env var in dev, `--session-api-key` injection in prod), the out-of-band prod build + fail-fast-missing-build contract (FR13b), and the PM2-supervision contract (FR11, FR13). A future rework must not silently reintroduce a bespoke launcher that duplicates PM2's own verbs, silently re-unify the two serving paths in a way that runs the dev server under `NODE_ENV=production` (regressing FR8/FR10 and re-introducing the `jsxDEV` crash), silently re-bake a server-local backend address into the browser bundle (regressing FR8a), silently fall through to an empty session key on either serving path (regressing FR8b and re-surfacing the "configure a backend" prompt), silently drop the prod build step / fail-fast-missing-build guard (regressing FR13b), nor drop the fail-fast `.dev-id` check that prevents silent port clashes, without revising this PRD first.

## Migration status

Implemented. The ecosystem is the self-deriving form (path → role, `.dev-id` → id/ports/namespace, three apps including the ingress); the bespoke launcher, the pre-PM2 shell supervisor, and the backend entry shim have been removed. `just dev` runs the stack in the foreground via `pm2-runtime` against a throwaway `PM2_HOME` (no dev-specific stop/restart/status/logs/save recipes); prod uses the detached `pm2 start` + `pm2 save` + `pm2 resurrect` lifecycle. The ingress wrapper `scripts/dev-local-ingress.mjs` is retained (see `docs/prd/4_ingress-host-wrapper.md`). The launcher auto-generates and persists the session API key (`~/.openhands/agent-canvas/dev-local-api-key`, `LOCAL_BACKEND_API_KEY` precedence, `OH_SESSION_API_KEY_PATH` override) so the frontend auto-configures the backend and never shows the "configure a backend" prompt on a fresh stack (FR8b).

The frontend is now served per role (FR8): dev runs `react-router dev`; prod runs the upstream `packages/agent-canvas/scripts/static-server.mjs` against a prebuilt SPA in the package's build directory, with the session key injected at runtime via `--session-api-key` and the same `backendRoutes` prefix set proxied to the backend. The prod build is regenerated out-of-band by `just setup --prod` (FR13b); `just setup` (no flag) skips it, so dev checkouts pay no build cost. The ecosystem's prod role fails fast if the build's `index.html` entry is missing. This split replaced an earlier form in which both roles ran `react-router dev` — the prod form crashed with `jsxDEV is not a function` because `NODE_ENV=production` makes Vite's SSR JSX transform import `react`'s production JSX runtime (no `jsxDEV`); serving a real production bundle under `NODE_ENV=production` is the fix.
