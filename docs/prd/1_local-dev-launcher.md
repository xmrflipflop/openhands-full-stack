# PRD: Local development launcher

**Status:** Active

## Summary

Run the Agent Canvas frontend and the OpenHands Agent Server backend together, built strictly from the source in this repository, so the two subtrees can be developed and validated against each other. The upstream `agent-canvas` CLI runs a similar stack but installs released artifacts (the agent-server from PyPI via `uvx`, the frontend from the published npm package); this workspace runs the same workflow pointed at local sources instead.

The stack is started by one launcher — `scripts/launch-stack.js`, the only supported entry point — which resolves every deployment-specific value (the per-checkout id, the app-name tag, ports, bind addresses, the session API key, `NODE_ENV`) and hands the result to PM2 as environment variables. A single committed `ecosystem.config.js` consumes those variables and defines the three PM2 apps; it **derives nothing** of its own and hard-errors (naming the launcher) if a required value is absent, so a bare `pm2 start ecosystem.config.js` fails immediately with an actionable message.

Mode and run style are two independent axes. **Mode** (`--production` or not) selects `NODE_ENV` and the frontend serving seam: development runs the Vite dev server, production serves a prebuilt bundle through the upstream static server — because the Vite dev server cannot run under `NODE_ENV=production`. **Run style** (`--background` or not) selects foreground `pm2-runtime` (default, with a throwaway `PM2_HOME` keyed on the tag) vs. detached `pm2` against the shared daemon. All four combinations are legal.

## Scope

Workspace-owned only; no upstream files are modified.

| Path | Role |
| --- | --- |
| `scripts/launch-stack.js` | The launcher and only supported entry point (workspace-owned). Parses flags, validates `.dev-id`, resolves ports, composes the tag, resolves the session key, performs the production build preflight, resolves the `--workspace_dir`-derived per-conversation working-dir base (`<workspace_dir>/project`) and `OH_*` agent-server data paths, and spawns PM2 (foreground `pm2-runtime` or detached `pm2`) with the resolved values as `STACK_*` env vars. Resolution is a pure function kept separate from spawning. |
| `ecosystem.config.js` | The single committed PM2 process ecosystem (workspace-owned), a pure consumer. Reads `STACK_*` / `NODE_ENV` from the environment the launcher sets and fans them out to the three apps; fans `STACK_WORKSPACE_DIR` / `STACK_CONVERSATIONS_DIR` / `STACK_BASH_EVENTS_DIR` to the backend as `OH_WORKSPACE_PATH` / `OH_CONVERSATIONS_PATH` / `OH_BASH_EVENTS_DIR`, and `STACK_VITE_WORKING_DIR` to the development frontend as `VITE_WORKING_DIR`; defines the uv-venv interpreter and supervision limits; selects the upstream serving seam by `NODE_ENV` (development: the Vite dev server; production: the static server + prebuilt SPA). Derives nothing; hard-errors naming the launcher if a required var is absent. The only conditional it contains is the `NODE_ENV` frontend branch, plus its production build preflight backstop. |
| `scripts/dev-local-ingress.mjs` | The single-origin ingress app (workspace-owned), the third PM2 app. A thin wrapper over the upstream ingress that adds only a bind address; its existence is justified in `docs/prd/4_ingress-host-wrapper.md`. |
| `scripts/prod-frontend-server.mjs` | The PM2 entry wrapper for the production frontend (workspace-owned). Imports `parseArgs` + `startStaticServer` from upstream and calls them unconditionally, bypassing the upstream `isMainModule` guard that fails under PM2 fork mode; its existence is justified in `docs/prd/6_prod-frontend-server-wrapper.md`. |
| `justfile` | The `setup` recipe bootstraps dependencies for every checkout (allocates `.dev-id`, `uv sync`, `npm install`); `just setup --production` additionally builds the Agent Canvas production bundle (the artifact the production static server serves). The `serve` recipe forwards all flags to the launcher unchanged. |
| `.gitignore` | Ignores the per-checkout identity file, the uv venv, node_modules, PM2 runtime state, and the production frontend build output. |
| `packages/OpenHands` | Consumed: the frontend dev server and its dev-proxy / configuration surface (development); the `static-server.mjs` static + reverse-proxy script and the `npm run build` target (production); the ingress script and proxy internals consumed by the wrapper. The package's `build/` directory (the production bundle output) is produced and consumed by the production path; it is gitignored and regenerated by `just setup --production`, not committed. |

### Retired by earlier revisions

Earlier forms of this functionality removed a pre-PM2 foreground shell supervisor, a bespoke PM2 launcher (a flag surface, hash-derived names, per-deployment `PM2_HOME` isolation, a "last started" name file, and orphan-reaping logic), and a backend entry shim. Those retirements stand; this revision does not reintroduce them.

### Changed by this revision

The ecosystem was previously self-deriving (role from the checkout path, identity/ports from `.dev-id`, `NODE_ENV` from role, session-key generation inlined). This revision moves all of that into the launcher and makes the ecosystem a pure consumer. See Decision points for the rationale. The `/opt`-as-prod-convention and the `prod`/`dev<N>` tag shape are removed; the tag is now `prod-<id>`/`dev-<id>`, production needs a `.dev-id`, and `just dev` is replaced by `just serve` (removed, not aliased). Snapshot/restore (`pm2 save` / `pm2 resurrect`) is dropped. These are breaking changes; running stacks under the old names need a manual `pm2 delete` before adopting the new shape.

## Functional requirements

- **FR1** — `scripts/launch-stack.js` is the only supported entry point. It resolves every deployment-specific value and hands off to PM2. It performs no supervision, holds no state between invocations, and duplicates none of PM2's verbs.
- **FR2** — The launcher's interface is flags, and nothing more: `--fe_port`, `--be_port`, `--ingress_port`, `--fe_bind`, `--be_bind`, `--ingress_bind`, `--workspace_dir` (all six default independently), `--background`, `--production`, `--dry-run`. Ports outside 1024–65535 or non-integer are a hard error.
- **FR19** — The launcher accepts a `--workspace_dir` flag (or `WORKSPACE_DIR` env var) to set the base directory for all agent-server data. It defaults to `<repo_root>/workspace`. From this base, it derives:
  - `OH_WORKSPACE_PATH` = `<workspace_dir>` (default workspace for conversations)
  - `OH_CONVERSATIONS_PATH` = `<workspace_dir>/conversations` (conversation storage)
  - `OH_BASH_EVENTS_DIR` = `<workspace_dir>/bash_events` (bash command history)
  This enables git worktree isolation where each checkout can have its own independent data directory that can be safely cleaned with `git clean`.
- **FR20** — The launcher derives a per-conversation working-dir base from the operator-chosen `workspace_dir` and hands it to the frontend as `VITE_WORKING_DIR`, so conversations started WITHOUT an explicit workspace land inside the configured tree instead of the upstream default `~/workspace/project/<id_hex>` (the relative "workspace/project" fallback constant resolved against the agent-server home dir). The base is `<workspace_dir>/project`, preserving the project-suffixed child dir under the workspace base that downstream code assumes (the `<id_hex>` sub-structure). It is emitted as `STACK_VITE_WORKING_DIR` and the ecosystem sets it as `VITE_WORKING_DIR` on the **development** frontend app env, where Vite exposes `VITE_*` process env to `import.meta.env` at dev-server start. Production does NOT honor it at serve time: `VITE_WORKING_DIR` is baked into a production bundle at `vite build` time, and the upstream static server has no runtime injection seam for it, so the served bundle honors a per-deployment `workspace_dir` only when rebuilt with the env set (e.g. `just setup --production` with `VITE_WORKING_DIR` exported). The launcher always derives and emits the value; whether the served bundle consumes it is a build-time concern, not a serve-time one.
- **FR3** — Every checkout carries a `.dev-id` containing a positive integer. Production is no longer exempt — the tag embeds the id. A `.dev-id` is required even when all ports are passed. A missing or invalid `.dev-id` aborts the launch. The launcher validates the id; it never allocates one. Allocation is owned by `docs/prd/5_devid-worktree-allocation.md`.
- **FR4** — The tag is `dev-<id>` or `prod-<id>`, used verbatim as the app-name suffix, the PM2 namespace, and the log subdirectory.
- **FR5** — Default ports are `base + id×10`, plus 5 for production. Bases are 3000 / 18000 / 9000 for frontend / backend / ingress. Ids start at 1. The production offset moves production off the round numbers so a development and a production of the same id (or same checkout) cannot collide; the step must stay larger than the offset, else different dev/prod ids could collide (a step of 1 would collide `dev-6` with `prod-1`). Each of the six ports defaults independently; a port flag overrides the computed default.
- **FR7** — The backend runs from local `packages/software-agent-sdk` sources and is launched with the repository's uv-managed virtual environment specified explicitly as PM2's `interpreter` (not system Python, not `uvx`, not a PyPI release). `uv sync` materialises the venv with workspace members in editable mode, so every `openhands-*` package resolves to local sources. No `openhands-*` release may be fetched from a registry. PM2's `script` points at the venv's installed `agent-server` console script; the venv python is the `interpreter`, so the composed command is the venv python running the installed console script and the installed package imports cleanly.
- **FR8** — The frontend is the local `packages/OpenHands` application; the published `@openhands/agent-canvas` package must never be installed or executed. The serving seam keys off `NODE_ENV`: development runs `react-router dev` (the Vite dev server, via the `dev:frontend` package script, whose dev proxy targets the backend); production runs the upstream `static-server.mjs` against the prebuilt production bundle, through a workspace-owned PM2 entry wrapper (`scripts/prod-frontend-server.mjs`, justified in `docs/prd/6_prod-frontend-server-wrapper.md`), with history-mode SPA fallback and its own reverse proxy forwarding the same backend path-prefix set as the ingress, so the production frontend port behaves like the dev server. This branch must survive: the Vite dev server cannot run under `NODE_ENV=production` (its SSR JSX transform then imports the production `jsx-runtime`, which has no `jsxDEV` export, and the server crashes with `jsxDEV is not a function`). No upstream file is patched; the ecosystem only configures the two upstream seams.
- **FR8a** — No server-local backend address (`host:port`) is baked into anything the browser executes. The frontend app's agent-server base URL resolves, at runtime in the browser, to the same origin that served the page: the launcher deliberately omits a browser-facing base-URL configuration so the app's same-origin fallback (the page's own origin when no base URL is configured) is what the browser uses. The same-origin promise is honored server-side by two paths — the ingress's prefix routes when the browser arrives through the ingress port, and (per mode) the Vite dev proxy's own entries or the static server's own reverse proxy when it arrives through the frontend port; both forward to the backend's loopback port on the server, where that address is valid. The launcher never branches on mode for the browser-facing env it exports.
- **FR8b** — The launcher guarantees a non-empty session API key — this is what makes the same-origin+key arrangement in FR8a actually suppress the "configure a backend" prompt (the frontend's default-local-backend constructor returns null on an empty key, which would re-surface that prompt regardless of the same-origin fallback). The exact resolution chain (moved verbatim from the ecosystem): an explicit `LOCAL_BACKEND_API_KEY` env var takes precedence; otherwise read the key persisted at a home-directory path (overridable via `OH_SESSION_API_KEY_PATH`); if that file is missing or empty, generate a fresh 256-bit (64-hex-char) key with the OS CSPRNG and persist it mode 0600 (a credential, never committed). The launcher passes the resolved key as a single `STACK_SESSION_API_KEY`; the ecosystem fans it out to three consumers — the backend key list, the dev-mode frontend's session-key env var, and the production static server's `--session-api-key`. The key is never baked into the build.
- **FR8c** — `--production` verifies the prebuilt frontend bundle exists and aborts if it is missing. The ecosystem repeats this check as a backstop so a re-evaluation (or a direct invocation) cannot silently serve nothing. The build is out-of-band — regenerated by `just setup --production` — and not part of the PM2 lifecycle.
- **FR9** — The whole stack is additionally served behind a single origin (the ingress app) that routes API and websocket path prefixes to the backend and everything else to the frontend, so the browser makes same-origin API/websocket calls. The ingress is the third PM2 app, run by `scripts/dev-local-ingress.mjs` (justified in `docs/prd/4_ingress-host-wrapper.md`). Its bind address is controllable (loopback by default; exposed on demand via the launcher's bind flag).
- **FR10** — `NODE_ENV` comes from `--production`: production only under `--production`, otherwise development (the default). It is set on all three apps. It is the only env-mode variable any application code reads (the frontend uses it for i18n debug logging and an `isDevMode` flag; the backend ignores it). There are no named runtime-environment blocks. This derivation is only sound because the serving seam is chosen to match `NODE_ENV` (FR8).
- **FR11** — PM2 supervises the frontend, backend, and ingress with bounded auto-restart: `autorestart`, a `max_restarts` limit, `min_uptime`, `restart_delay`, `kill_timeout`, and a `max_memory_restart` threshold. A process that repeatedly fails within its minimum-uptime window is held in an `errored` state rather than spinning.
- **FR12** — The stack runs unprivileged: no port below 1024 is bound, and all writes stay inside the checkout. Root is not required for normal operation. Privilege drop via PM2 `uid`/`gid` is documented but disabled by default and only honoured when PM2 is started as root.
- **FR13** — Mode (FR8/FR10) is independent of environment; all four combinations are legal. Foreground (default) runs `pm2-runtime start` with a throwaway `PM2_HOME` keyed on the tag, so the foreground run never touches the global daemon. `--background` runs `pm2 start` against the shared daemon. (Note the runner mapping reads "backwards" but is correct: `pm2-runtime` is the foreground runner; `pm2 start` detaches.)
- **FR14** — `just serve *args` forwards all arguments to the launcher unchanged, in the foreground. It replaces `just dev`, which is removed — not aliased. There are no dev-specific stop/restart/status/logs/save recipes; foreground `pm2-runtime` and PM2's own verbs cover everything.
- **FR15** — The ecosystem derives no identity or deployment value: it never reads `.dev-id`, never infers environment from its location, never computes a port, never generates a credential, and never applies a bind default. It hard-errors — naming the launcher — if any required `STACK_*` var is absent. It does still use `__dirname` for path composition only. The `LOCAL_BACKEND_API_KEY`, `OH_SESSION_API_KEY_PATH`, and legacy `DEV_*_BIND` inputs are launcher-only; the ecosystem reads none of them.
- **FR16** — PM2 app names are `<service>-<tag>`; the PM2 `namespace` is the tag; logs are partitioned by tag and service under a gitignored tree so concurrent checkouts don't clobber one another.
- **FR17** — Bind addresses are launcher-owned, one per service, defaulting to `127.0.0.1`. Precedence is flag, then the legacy `DEV_*_BIND` env var (kept for continuity with existing shell profiles), then loopback. The launcher passes them to the ecosystem as `STACK_*_BIND`; the ecosystem no longer reads `DEV_*_BIND` and applies no default of its own. The loopback default is a security property, not a convenience — binding wider exposes an unauthenticated-by-default stack, so it must stay opt-in and explicit. FR12 still holds: no port below 1024.
- **FR18** — `--stop` (and `just serve --stop`) stops and deletes the background stack for this checkout by reading `.dev-id` and deleting the matching namespace from the shared PM2 daemon. Respects `--production`: `just serve --stop` stops `dev-<id>`; `just serve --production --stop` stops `prod-<id>`. This lets the operator stop one mode while leaving the other running. Idempotent: exits 0 if nothing was running. Ignores all other flags; only `.dev-id` (and the `--production` flag for namespace selection) are required.

### Interface contract

The launcher sets, the ecosystem reads, and all are hard-error if absent except `NODE_ENV` (defaults to development): `STACK_FE_PORT`, `STACK_BE_PORT`, `STACK_INGRESS_PORT`, `STACK_FE_BIND`, `STACK_BE_BIND`, `STACK_INGRESS_BIND`, `STACK_TAG`, `STACK_SESSION_API_KEY`, `NODE_ENV`. `LOCAL_BACKEND_API_KEY`, `OH_SESSION_API_KEY_PATH`, and the legacy `DEV_*_BIND` vars become launcher-only inputs — the ecosystem reads none of them.

## Non-functional requirements

- **NFR1** — The launcher is Node (PM2 guarantees Node is present). No Python: system `python3` isn't guaranteed, and the SDK venv may not exist yet at launch time.
- **NFR2** — Values are resolved once at launch and fixed for the stack's life.
- **NFR3** — Snapshot/restore is dropped. There is no `pm2 save`, no resurrect handling, and no reboot survival. A restored snapshot would replay stale values and persist the session key to disk, so it is intentionally unsupported; restart by re-running `just serve`.
- **NFR4** — Nothing is committed: `.dev-id`, venvs, node_modules, PM2 runtime state, and the production build output are all gitignored.
- **NFR5** — Concurrent checkouts never collide: the id is the single source of truth for names and ports, and an invalid `.dev-id` fails fast.
- **NFR6** — Resolution is a pure function, testable without PM2. It is kept separate from spawning.

## Decision points

- **Why the self-deriving ecosystem was reversed.** The earlier ecosystem derived role and identity (and generated the session key) at evaluation time, from the checkout path and `.dev-id`. This made the ecosystem's behavior implicit and untestable: the resolution logic ran as a side effect of PM2 evaluating the file, could not be exercised without PM2, and could not be dry-run or given a flag surface. Moving every resolution into an explicit launcher keeps one source of truth (the launcher) and makes the ecosystem a small, dumb consumer that does nothing but fan known values out to apps — a bare `pm2 start` now fails with an actionable message instead of silently picking a deployment. The launcher is the seam that owns flags, validation, the preflight, and the spawn; the ecosystem is the seam that owns app definitions, supervision, and the `NODE_ENV` serving branch.
- **Why mode is orthogonal to environment.** The earlier design conflated "production" (an environment) with "detached" (a run style) via the `/opt`-path convention, so a prod checkout could only be started detached and a dev checkout could only run foreground. That coupling was arbitrary: an operator may want to run a production build in the foreground to watch logs, or detach a development stack while continuing other work. Mode (`--production`, selecting `NODE_ENV` and the serving seam) and run style (`--background`, selecting the PM2 runner) are now separate axes, and all four combinations are legal. Production is no longer inferred from the checkout path — it is selected explicitly with `--production`.
- **Why the production port offset is 5 and the step is 10.** Production and a development run of the same checkout (or the same id) must not collide on ports or names. Giving production a `+5` offset on top of `id×10` moves it off the round numbers so `dev-1` and `prod-1` get distinct ports; the dev/prod branches of the same checkout can then technically run simultaneously. The step (10) must stay larger than the offset (5): if the step were 1, `dev-6` (base+6) would collide with `prod-1` (base+1+5). The offset is documented as a fixed 5 and the step as a fixed 10; both are load-bearing.
- **Why snapshot/restore was dropped.** `pm2 save` / `pm2 resurrect` snapshot the resolved per-app environment and replay it after a machine restart. Under the new model that environment is the launcher's output, resolved fresh on every start; a replayed snapshot would (a) reuse stale values (old id, old ports, a build path that may no longer match the source) and (b) persist the session API key to PM2's on-disk dump. Restart-by-re-launch is safer than restore-from-snapshot, so there is no resurrect handling and no reboot-survival path; the operator re-runs `just serve`.
- **Node over Python for the launcher.** PM2 itself guarantees a Node runtime is present (it is a Node process), so a Node launcher has zero unmet dependencies. A Python launcher was rejected because system `python3` is not guaranteed on every host, and the SDK's uv venv — the natural place to find a known Python — may not exist yet at the moment the launcher runs (the very first `just serve` on a fresh checkout precedes a successful `uv sync`). Node has neither problem.

## Assumptions (re-check these first when upstream changes)

- The `packages/OpenHands` subtree is sourced from the OpenHands monorepo (OpenHands/OpenHands), whose repository root is the `@openhands/agent-canvas` frontend. The git remote is `OpenHands`; its URL and the release-fetch slug point to the monorepo. Every "Re-check on upstream sync" note below applies to the monorepo's frontend root after each `just sync`.
- `pm2` (any current v7+) is installed on contributor machines, in CI, and in any deployment image. The launcher spawns `pm2-runtime` (foreground) and `pm2` (background) by name from `PATH`; both ship with pm2.
- The SDK remains a single uv workspace whose members include the agent-server; it exposes a runnable agent-server entry point accepting host and port options; and `uv sync` materialises a `.venv` whose `python` can import and run the agent-server entry function.
- The frontend keeps a `dev:frontend` package script that starts only the dev server (without spawning backends), honours environment configuration for its port and backend host, and proxies API/websocket path prefixes to the configured backend. (Consumed only by the development serving path.)
- The frontend ships a `build` / `build:app` package script that produces a production SPA bundle whose entry is `index.html` with the hashed assets under it. The production static server serves that directory. **Re-check on upstream sync**: if the build output layout changes, update the production stat path and the `--dir` path passed to the static server; the build preflight keys on that entry file.
- The frontend ships a `packages/OpenHands/scripts/static-server.mjs` that accepts `--dir`, `--port`, `--host`, `--route <prefix=url>` (repeatable, websocket-aware), `--session-api-key` (injects `window.__AGENT_CANVAS_SESSION_API_KEY__` into the served `index.html` at runtime), and history-mode SPA fallback. The production frontend app pins to that script's CLI surface. **Re-check on upstream sync**: if the flag names, the key-injection seam (`__AGENT_CANVAS_SESSION_API_KEY__` → `getBakedSessionApiKey()`), or the injection mechanism change, update the production frontend args and re-assert FR8b for the served bundle before relying on it.
- The Vite dev server still cannot run under `NODE_ENV=production`. Under `NODE_ENV=production`, Vite's SSR JSX transform imports `react`'s production `jsx-runtime` (which exports `jsx`/`jsxs` but **no** `jsxDEV`), while the compiled entry-server calls `jsxDEV`, so the dev server crashes with `jsxDEV is not a function` (and a downstream `Cannot access 'abort' before initialization` TDZ crash from the abort timer). This is the load-bearing reason the serving seam keys off `NODE_ENV` (FR8). **Re-check on every upstream sync**: if Vite or `react` ever changes so the dev server can run under `NODE_ENV=production`, the FR8 serving split could be relaxed — but not before re-asserting that no dev-server path ships to production with HMR plumbing, and not without revising this PRD first.
- The frontend's dev-proxy host configuration (`VITE_BACKEND_HOST`) is consumed only server-side by the Vite config, never by the browser-side app; it is distinct from the browser-side base-URL configuration. (Development only.)
- **Same-origin fallback (the load-bearing assumption for FR8a).** The frontend app's agent-server base-URL lookup returns a configured base URL when one is present, and otherwise falls back to the page's own origin (`window.location.origin`). The launcher relies on this fallback to *never* bake a server-local address into the browser bundle. **Re-check this first on every upstream sync**: if upstream ever makes a configured base URL mandatory (no fallback, or the fallback removed), the launcher's withholding of that URL would re-surface the "configure a backend" prompt for remote browsers, and a replacement same-origin mechanism must be found before the stack can be sync'd.
- **Session-key-onboarding interplay (the second load-bearing assumption for FR8a / the one that drove FR8b).** The frontend's default-local-backend constructor (`makeDefaultLocalBackend()`) returns null unless **both** a non-empty base URL *and* a non-empty session API key are available — an empty/whitespace key is treated as missing, so the backend registry is left empty and the "configure a backend" onboarding prompt fires regardless of the same-origin fallback. The launcher MUST therefore guarantee a non-empty key for both serving paths: in development by exporting a non-empty `VITE_SESSION_API_KEY` (consumed at build/dev time), and in production by passing the same key to `static-server.mjs --session-api-key`, which the static server injects into the served `index.html` as `window.__AGENT_CANVAS_SESSION_API_KEY__` (read at boot by `getBakedSessionApiKey()`). **Re-check on upstream sync**: if either the env-var consumer OR the `--session-api-key` → `getBakedSessionApiKey()` injection seam is removed, the corresponding serving path would silently regress to an empty key and re-surface the onboarding prompt; a replacement seam must be wired on the affected path before the stack can be sync'd.
- The frontend's backend-host configuration (development) accepts a `host:port` value that the dev proxy forwards to, the static server's `--route` values (production) accept `<prefix>=http://host:port`, and the frontend's backend-base-URL configuration (when set at all) accepts a full `http://host:port` value the browser uses directly.
- **Per-conversation working dir (load-bearing for FR20).** The frontend decides a conversation's `working_dir` when the user starts a conversation WITHOUT picking an explicit workspace, via `buildConversationWorkingDir()` in `packages/OpenHands/src/api/agent-server-config.ts` = `<getAgentServerWorkingDir()>/<id_hex>`. `getAgentServerWorkingDir()` reads `import.meta.env.VITE_WORKING_DIR` and falls back to the constant `DEFAULT_WORKING_DIR = "workspace/project"` (a *relative* path). The relative value is then resolved against the agent-server's home dir by `resolveAbsoluteAgentServerPath()` in `packages/OpenHands/src/api/agent-server-home.ts` (the `WUP-001` spec comment explains the `/`-prepending fallback is deliberately avoided so relative dirs land at `~/workspace/project/<id_hex>` rather than read-only `/workspace/...`). **Re-check on every upstream sync**: if `VITE_WORKING_DIR` is renamed/removed, the env var set on the dev frontend app (FR20) stops taking effect and conversations regress to `~/workspace/project/<id_hex>`. The development path honors the env at dev-server start (Vite statically exposes `VITE_*` process env to `import.meta.env`), but a production bundle bakes `VITE_WORKING_DIR` at `vite build` time and the upstream static server (`packages/OpenHands/scripts/static-server.mjs`) has no runtime injection seam for working dir (it injects only the session key, auth flag, runtime services, lock-to-cloud, and base path as `window.__AGENT_CANVAS_*` globals) — so production honoring a per-deployment `workspace_dir` requires a rebuild, not a serve-time env.
- The workspace's `backendRoutes` list (`/api`, `/sockets`, `/server_info`, `/alive`, `/health`, `/ready`, `/docs`, `/redoc`, `/openapi.json`) tracks the Vite dev-proxy prefix list (`packages/OpenHands/vite.config.ts`). It is shared by the ingress (both modes) and the production static server's `--route` flags. **Re-check on upstream sync**: if the Vite dev-proxy prefix set changes (paths added/removed/renamed), update `backendRoutes` in the ecosystem in the same change so all three proxying paths keep routing identically.

## Upstream divergence

No upstream code is modified; the divergence is behavioral. Upstream's launcher installs released artifacts by design; this one forbids that and runs local sources, so it is not upstreamable as-is. If upstream ever ships a supported "run everything from a local checkout" mode covering both projects, this functionality can be retired in its favor.

The PM2 ecosystem and the launcher are workspace-owned; they are not upstream contributions because upstream neither supervises its launcher with PM2 nor separates resolution from supervision this way. The backend launch uses the SDK's own installed `agent-server` console script (no workspace-owned backend entry file). The production frontend app launches the upstream `static-server.mjs` through a workspace-owned PM2 entry wrapper (`scripts/prod-frontend-server.mjs`, `docs/prd/6_prod-frontend-server-wrapper.md`) and builds the upstream `build`/`build:app` target — both only configured/consumed, not patched. The `NODE_ENV`-based choice of which upstream seam to serve the frontend through (development: `react-router dev`; production: `static-server.mjs` via the wrapper) is workspace behavior layered on top of upstream's existing two serving modes; upstream never needs to adopt it.

## Conflict resolution notes

Preserve the requirements, not the implementation. If an upstream update breaks the stack, re-locate the SDK's current way of running the agent-server from workspace sources (`uv sync` + the venv python) and the frontend's current dev-server script and configuration surface (development), the current `build`/`build:app` target and its output layout (production build), and the current `static-server.mjs` CLI surface and runtime key-injection seam (production serve), then rewire the launcher and the ecosystem to them. Any functional requirement may be reimplemented with different mechanics; none may be dropped silently.

The stable invariants are: the launcher-as-only-entry-point contract (FR1, FR15); the required `.dev-id` for every checkout including production (FR3); the `dev-<id>`/`prod-<id>` tag and the `base + id×10 (+5 for production)` port contract with step greater than offset (FR4, FR5); the local-sources-only contract (FR7–FR8); the uv-venv-as-interpreter contract (FR7); the `NODE_ENV`-appropriate-serving-seam contract (FR8 — the dev server MUST NOT run under `NODE_ENV=production`); the no-baked-server-local-address / same-origin contract (FR8a — honored on both serving paths via the ingress or the static server's own proxy); the guaranteed-non-empty-session-key contract on both serving paths, resolved once in the launcher and fanned to three consumers (FR8b); the out-of-band production build and the fail-fast-missing-build guard, run by the launcher and repeated by the ecosystem (FR8c); the single-origin ingress contract (FR9); the `NODE_ENV`-from-mode contract (FR10); the PM2-supervision limits including `kill_timeout` (FR11); the unprivileged / no-port-below-1024 contract (FR12); the mode-independent-of-run-style contract and the throwaway `PM2_HOME` keyed on the tag for foreground runs (FR13); the loopback-default-is-a-security-property contract for binds (FR17); the `--stop` teardown mechanism that respects `--production` to stop only the matching namespace (`dev-<id>` or `prod-<id>`) (FR18); the `--workspace_dir`-derived per-conversation working-dir base exported as `VITE_WORKING_DIR` on the dev frontend app (FR20 — dev honors it at serve time; prod requires a rebuild since the static server has no working-dir injection seam); and the dropped snapshot/restore (NFR3).

A future rework must not, without revising this PRD first: silently reintroduce a bespoke launcher that duplicates PM2's own verbs; silently re-unify the two serving paths in a way that runs the dev server under `NODE_ENV=production` (regressing FR8/FR10 and re-introducing the `jsxDEV` crash); silently re-bake a server-local backend address into the browser bundle (regressing FR8a); silently fall through to an empty session key on either serving path (regressing FR8b and re-surfacing the "configure a backend" prompt); silently drop the production build preflight (regressing FR8c); silently drop the fail-fast `.dev-id` check that prevents silent port clashes (FR3); silently make the ecosystem self-deriving again (regressing FR15); silently reintroduce snapshot/restore (regressing NFR3); silently change the loopback bind default to something wider (regressing FR17's security property); or silently remove the `--stop` / `just serve --stop` teardown mechanism that provides reliable, idempotent cleanup across branch switches (regressing FR18).
